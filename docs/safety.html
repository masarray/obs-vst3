Safety model · v0.6.0

A bad plug-in should not be allowed to become a bad broadcast.

VST3 plug-ins are native code. OBS Safe VST3 Host changes the failure boundary by keeping third-party VST3 DSP and vendor GUI code outside obs64.exe in both the Single Host and VST3 Rack workflows.

The core boundary

OBS Studio (obs64.exe) │ ├─ VST 3.x Plug-in ── bounded IPC ──► obs-safe-vst3-host.exe │ └─ one VST3 + vendor UI │ └─ VST3 Rack ── Rack IPC ─────► obs-safe-vst3-rack-host.exe ├─ graphical Rack Editor ├─ serial VST3 chain └─ vendor UI windows VST3 discovery ─────────────────────────► obs-safe-vst3-scanner.exe

What isolation does

  • Single Host runtime: third-party VST3 DSP and vendor GUI run in obs-safe-vst3-host.exe.
  • Rack runtime: Rack VST3 DSP, Rack Editor and vendor-editor ownership live in obs-safe-vst3-rack-host.exe.
  • Scanning: normal candidate probing is performed outside OBS.
  • Recovery: helper health, state restoration and bounded restart behavior are explicit product concerns.

What happens to audio when an isolated result is unavailable?

The realtime OBS side is designed around bounded work. If a valid processed wet block is late, invalid or unavailable, the product keeps the original dry/pass-through audio instead of deliberately waiting without bound.

During a live show, losing an effect is preferable to intentionally stalling the broadcast audio callback.

State, Rack snapshots and presets

The Single Host persists VST3 state for recovery. The Rack adds a working Session Snapshot model and named reusable presets. Missing Rack plug-ins can remain pass-through placeholders, and a failed/corrupt preset load is not allowed to replace the current working Rack.

Bounded shutdown

v0.6.0 includes explicit Rack helper shutdown hardening so a hung isolated helper is not allowed to hold OBS shutdown indefinitely. This is part of the same product principle: an out-of-process VST3 failure must remain bounded at the OBS boundary.

Can this promise OBS will never crash?

No. Windows, OBS itself, drivers, hardware faults and other native components remain outside this project's control. The defensible claim is architectural: third-party VST3 runtime and vendor UI code are deliberately kept outside the OBS process.

Crash isolation is not a malware sandbox

The helper processes run with your Windows user permissions. A malicious VST3 can still use APIs and resources available to your account.

Only install VST3 plug-ins from vendors you trust. Process isolation here is designed for crash/hang containment and bounded recovery—not for safely running untrusted malware.

Release confidence

The public Windows pipeline rebuilds against pinned OBS/libobs, runs automated tests and scanner smoke, validates the package and Smart Installer, and publishes SHA-256 checksums beside the binaries. Rack integration also has focused serial-processing, safety, topology, recovery, editor, vendor-UI and preset regression gates.

Automated tests cannot prove every commercial plug-in on every Windows machine, so compatibility claims remain conservative and real-machine evidence remains important.

Unsigned Windows package

The current package is not commercially Authenticode-signed. Windows may show Unknown publisher or a SmartScreen reputation warning.

Do not disable Windows security globally. Download only from the official GitHub Releases page and compare against SHA256SUMS.txt when you want an additional integrity check.

Get-FileHash .\OBS-Safe-VST3-Host-v0.6.0-Setup-x64.exe -Algorithm SHA256
